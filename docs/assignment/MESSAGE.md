# Контракт Поручения

**Поручение** — единица обмена в модели [«Роли и Функции»](MODEL.md): сообщение, которым один Исполнитель передаёт другому **работу и смысл** (проблему, цель, контекст). Поручение — это **результат работы автора**: он его создаёт и уступает ход; вложенной блокирующей рекурсии нет.

Одна и та же структура покрывает и «сделай вперёд», и «выясни/сообщи», и «готово» — различает их **тип** (см. ниже). Поручение состоит из **конверта** (адресация и связи — забота [Координатора](COORDINATOR.md)) и **тела** (смысл — забота Исполнителя).

За основу тела взята рекомендуемая структура Product Requirements Document, но **переосмысленная**: не «документ о продукте», а **о текущей проблеме и цели** конкретной передачи работы. Имя «PRD» намеренно не используется — оно не передаёт смысл этого документа.

---

## Конверт

Адресная и связующая часть. Словарь опирается на **FIPA ACL** (стандарт агентной коммуникации).

| Поле | Назначение | Аналог в FIPA ACL |
| --- | --- | --- |
| **Номер** | Сквозной идентификатор в едином реестре; нумерация как у ADR (`001`, `002`, …) | — |
| **Тип** | Намерение сообщения (см. таблицу типов) | `performative` |
| **От (функция)** | Функция-автор | `sender` |
| **К (функция / способность)** | Адресат: конкретная функция или **требуемая способность**, если исполнитель заранее неизвестен | `receiver` |
| **Нить** | Идентификатор диалога/процесса, к которому относится Поручение | `conversation-id` |
| **В ответ на** | Номер Поручения, на которое это отвечает | `in-reply-to` |
| **Происхождение** | Номера входных Поручений, из которых выведено это (рёбра графа) | — |
| **Статус** | `новое` / `в работе` / `ожидает ответа` / `выполнено` / `эскалировано` | — |
| **Дата** | Момент создания | — |

Маршрутизацию по полю «К» и ведение реестра выполняет Координатор; Исполнитель заполняет остальное.

## Типы Поручения

| Тип | Смысл | Направление |
| --- | --- | --- |
| **ПОРУЧИТЬ** | Передать работу вперёд: «вот проблема и цель — сделай» | Вперёд по процессу |
| **ЗАПРОСИТЬ** | Не хватает информации: «мне нужно узнать X, вот зачем» | К владельцу способности |
| **СООБЩИТЬ** | Ответ/информация на запрос | Обратно инициатору |
| **ГОТОВО** | Функция выполнена; результат (deliverable) прилагается | Вперёд / Пользователю |
| **ЭСКАЛАЦИЯ** | Нужно решение человека (см. HITL в [COORDINATOR.md](COORDINATOR.md)) | К Пользователю |
| **ВЕТО / СИГНАЛ** | «Выполнил как поручено, но считаю решение спорным» — продуктовое вето, не блокирующее исполнение | Вперёд + Пользователю |

Тип **ВЕТО / СИГНАЛ** введён сознательно: в эксперименте исполнение «по букве» верной, но продуктово спорной постановки (эпизод #51) некуда было выразить. Это отдельный тип, чтобы сигнал о спорности не терялся и не подменялся молчаливым исполнением.

## Тело

Смысловая часть. Поля — предметно-независимые (без веб-акцента). Для типа **ЗАПРОСИТЬ** используется облегчённый профиль (см. ниже).

| Поле | Что содержит | Обязательность |
| --- | --- | --- |
| **Резюме** | Кратко: кого касается проблема, масштаб, ожидаемый результат | Обязательно |
| **Проблема** | Формулировка проблемы, которую должен закрыть адресат | Обязательно (ядро) |
| **Смысл / контекст** | Зачем это, как связано с общим процессом; фон, нужный для понимания | Обязательно |
| **Почему сейчас** | Актуальность/приоритет | Опционально; часто наследуется от родительского Поручения по ссылке |
| **Целевой исполнитель** | Кому адресовано **по смыслу** (способность/функция); *не* путать с благополучателем из «Резюме» | Обязательно (может быть «способность», не конкретный Актор) |
| **Цели и не-цели** | Что считается достигнутым; что сознательно не является целью | Обязательно |
| **Критерии приёмки** | Наблюдаемый результат, по которому **адресат сам** проверит, что справился | Обязательно |
| **Функциональные требования (MoSCoW)** | Что должно уметь решение: Must / Should / Could / Won't | Обязательно для **ПОРУЧИТЬ** |
| **Ограничения** | Качественные рамки (в предметной области раскрываются как производительность, безопасность, совместимость и т.п.) | Опционально |
| **Ключевые сценарии** | Как результатом будут пользоваться — носитель «смысла» | Рекомендуется |
| **Зависимости и риски** | От чего зависит; что может пойти не так | Рекомендуется |
| **Вне рамок** | Явный список того, чего **не будет** (уровень охвата; дополняет «не-цели») | Обязательно |
| **Открытые вопросы** | Честный список нерешённого, что автор передаёт дальше вместо молчаливого допущения | Обязательно |

### Облегчённый профиль для ЗАПРОСИТЬ

Запрос информации не требует полного тела. Минимум: **Проблема** (чего не хватает), **Смысл / контекст** (зачем), **Целевой исполнитель** (нужная способность), **Критерии приёмки** (какой ответ закроет запрос). Остальные поля — по необходимости.

## Пять инвариантов

Условия работоспособности; каждый закрывает конкретный провал эксперимента.

1. **Самодостаточность для адресата.** Из Поручения понятны проблема, цель, смысл и критерии — без доступа к «памяти» автора. (Субагент стартует с чистого листа; ср. находка о неравномерной самодостаточности.)
2. **Открытые вопросы обязательны.** Поле «Открытые вопросы» — единственный легальный канал передать нерешённое дальше. Пустым оно допустимо, только если нерешённого действительно нет.
3. **Критерии приёмки самопроверяемы адресатом.** Формулируются от способности **получателя** проверить себя, а не «как задумал автор». Иначе воспроизводится разрыв «зелёный вердикт ≠ исполнимость».
4. **Реестр — граф происхождения.** Поля «Происхождение» и «В ответ на» образуют граф; он же даёт аудит-след и восстанавливает структуру, теряемую в плоском списке. Ведёт [Координатор](COORDINATOR.md).
5. **Неизменяемость + замещение.** Принятое Поручение **не переписывается** (как ADR). Разрешение открытого вопроса или уточнение порождает **новое** Поручение, ссылающееся на исходное; знание не теряется в переписке.

## Границы

- Поручение — **коммуникационный артефакт**, а не спецификация требований. Его нагрузка может содержать требования, но само оно не заменяет работу по инженерии требований.
- Свойства IEEE 830 — **ориентир** качества формулировок тела, не жёсткая рамка: не превращать Поручение в самодостаточный тест-спек.
- Нумерация и хранение реестра Поручений — **шире GitLab AI Helper** и не завязаны на его историю версий Issue.
